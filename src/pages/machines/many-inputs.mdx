A machine is one rule, written once. What makes it worth drawing is
that the one rule answers a different question for every input you
hand it, and it answers all of them the same way: by walking.

So far we have watched one string at a time. On this page we hand a
machine *everything*. Every input of length 0, then every input of
length 1, then length 2, and so on. The verdicts arrive in a block,
and the pattern in that block is what the machine is actually for.

Each runner below has a panel underneath it listing every short
input, coloured by its verdict. Click any one to watch it walk.
**Run them all** plays through the whole list in order.

## Thirty-one inputs, one two-state machine

Here is a two-circle machine with a job to do. It accepts a string
exactly when the last symbol is a `0`.

<FSMRunner
  client:visible
  machine={endsInZero}
  defaultInput="1010"
  examples={["", "0", "1", "10", "01", "111", "1010"]}
  sweep={{ maxLength: 4 }}
/>

Look at the green chips as a block rather than one at a time. Every
accepted string ends in `0`, and every string that ends in `0` is
accepted, whatever else is in it. Length has nothing to do with it.
Neither does the beginning. The machine has two circles and it has
never once needed to know more than one thing.

The trail under the diagram is where that becomes obvious. Watch
where the same four walks end up.

<FSMTraceTable
  client:load
  machine={endsInZero}
  inputs={["0", "10", "1110", "0000"]}
  caption="four different inputs, four different walks, one shared last step"
  notes={{
    "0": "one symbol and it is already there",
    "10": "a detour, then back",
    "1110": "three symbols wasted, so to speak",
    "0000": "it never leaves",
  }}
/>

The four walks have nothing in common until the very last hop, and
after that last hop they are indistinguishable. That is the whole
design. The machine is not storing the input. It is storing the one
fact about the input that the question depends on, and throwing away
everything else as it goes.

## Near misses

Now a machine that has to hold on to a little more: it accepts when
the input *ends* in `101`. Open the panel and read the length-4 row.

<FSMRunner
  client:visible
  machine={endsIn101}
  defaultInput="10101"
  examples={["101", "0101", "1101", "10101", "1011", "1010"]}
  sweep={{ maxLength: 4 }}
/>

Two strings in that row deserve a minute each.

<FSMTraceTable
  client:load
  machine={endsIn101}
  inputs={["101", "1010", "1011", "10101"]}
  caption="the same machine on four inputs that all contain 101"
  notes={{
    "101": "arrives and stops there",
    "1010": "arrives, then one more symbol carries it out again",
    "1011": "arrives, then leaves, but not all the way back",
    "10101": "arrives, leaves, and arrives again",
  }}
/>

`1010` reaches the accepting circle and then walks out of it. The
`101` is still sitting in the string, but no longer at the end, and
the end is what the question asked about. Reaching an accepting
state is not a prize you keep. It is a place you happen to be
standing when the input runs out.

`1011` is the one that catches people. A first guess sends the
machine all the way back to the start, on the grounds that the run
of `101` has been spoilt. Follow the trail instead. The input now
ends in `1`, and `1` is the first symbol of `101`, so one symbol of
progress is already banked. Throwing it away would cost the machine
the string `101101`, which it ought to accept.

Step through `1011` with the **Step** button and watch the *remembering*
line under the trail. It never says anything about the whole input. It
only ever says how much of `101` is currently sitting at the end.

## A door that closes behind you

The next machine accepts a string when every uninterrupted run of
`1`s in it has even length. The run `11` is fine. The run `111` is
not.

<FSMRunner
  client:visible
  machine={evenBlocksOfOnes}
  defaultInput="0110011"
  examples={["", "11", "0110011", "010", "111", "0111011"]}
  sweep={{ maxLength: 4 }}
/>

Something new is visible in this panel. Find the string `010`, which
is rejected, and then look at every longer string that begins with
`010`. All of them are rejected too. There is no rescue.

Compare that with `1`, which is also rejected, and where the longer
strings starting with `1` are a mixed bag: `11` is accepted, `110`
is accepted, `111` is not.

<FSMTraceTable
  client:load
  machine={evenBlocksOfOnes}
  inputs={["1", "11", "010", "0101"]}
  caption="rejected for two quite different reasons"
  notes={{
    "1": "not accepted, but one more 1 would fix it",
    "11": "the fix",
    "010": "the 0 closed a run of length one, which is odd",
    "0101": "already beyond rescue, so the extra 1 changes nothing",
  }}
/>

So the machine has two different ways of saying no, and it needs two
different circles to say them. `odd` means *not yet*. `dead` means
*never*. Running a machine on many inputs is how you notice the
difference: a state is a dead end exactly when everything downstream
of it is red.

## When the input is a number

The last machine on this page reads its input as a number written in
binary, and accepts when that number is a multiple of 5. It never
holds the number. It holds only the remainder, and there are five of
those.

<FSMRunner
  client:visible
  machine={divBy5Binary}
  defaultInput="1010"
  examples={["0", "101", "1010", "1111", "10100", "1011"]}
  width={600}
  sweep={{ maxLength: 5 }}
/>

Read the accepted strings out of the panel and turn each one into a
number: `0` is 0, `101` is 5, `1010` is 10, `1111` is 15, `10100` is
20, `11001` is 25, `11110` is 30. The green chips are exactly the
multiples of 5, in order, with their leading zeros thrown in as
well.

Now step through `1111` slowly and watch the *remembering* line. It
says 1, then 3, then 2, then 0. Those are the remainders of 1, 3, 7
and 15 on division by 5. The machine is doing arithmetic it never
writes down, on a number it never knows.

## Two habits worth keeping

**Predict, then run.** Before clicking a chip, say out loud which
circle the walk will finish in. Being wrong is the useful outcome,
because a wrong prediction points straight at the arrow you have
misread.

**Read the trail, not the picture.** The diagram tells you what the
machine could do. The trail tells you what it did. Almost every
mistake in this chapter is a disagreement between the two, and the
trail is always right.
