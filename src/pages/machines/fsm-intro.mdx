A **finite state machine** can be in one of a few **moods** at any
moment, and reacts to whatever you feed it next according to a rule
that depends only on its current mood and the next thing it sees.
That's the whole story.

We draw a machine as circles (one per mood) connected by labelled
arrows. The **start** mood has a stub arrow from outside; an
**accepting** mood — one we'd like to end in — has a double border.

## A light switch

The smallest machine worth drawing. Two moods, **Off** and **On**,
and one input, <code>f</code> for *flick*. A flick swaps you. Press
**Play** below.

<FSMRunner
  client:visible
  machine={lightSwitch}
  defaultInput="ffff"
  examples={["", "f", "ff", "fff", "ffff"]}
/>

The four pieces of a machine are:

- a finite set of **states** (drawn as circles),
- an **alphabet** of input symbols,
- **transitions** (one outgoing arrow per state per symbol),
- a designated **start** state and a set of **accepting** states.

For the machine to be well-defined, *every* state must have an
outgoing arrow for *every* symbol. When a rule like "if the first
symbol is wrong, give up" needs to be enforced, we send the machine
to a **dead** state — non-accepting, looping on every input.

## The turnstile

A subway turnstile has two moods, **Locked** and **Unlocked**, and
two inputs, <code>c</code> for *coin* and <code>p</code> for *push*.
A coin unlocks; a push locks. There are no accepting states — the
turnstile is modelling continuous behaviour, not a yes/no test on
a string.

<FSMRunner
  client:visible
  machine={turnstile}
  defaultInput="cpcp"
  examples={["", "p", "c", "cp", "cc", "cpcp", "ppc"]}
/>

## Ending in 0

A two-state recognizer. The machine remembers one fact about the
input so far: *did the last symbol I read equal <code>0</code>?*
That single bit of memory is enough to know whether to accept.

<FSMRunner
  client:visible
  machine={endsInZero}
  defaultInput="1010"
  examples={["", "0", "1", "10", "01", "100", "111", "1010"]}
/>

## Ending in 101

The same idea, with a longer memory. Each mood is named after *how
much of* <code>101</code> *currently sits at the end of the input* —
nothing, <code>1</code>, <code>10</code>, or the whole thing.

<FSMRunner
  client:visible
  machine={endsIn101}
  defaultInput="10101"
  examples={["101", "0101", "1101", "10101", "10", "011", "1010", "1011"]}
/>

Watch the two arrows leaving <code>101</code>, because they are where
a first attempt usually goes wrong. A <code>1</code> does *not* send
you back to the start: the input now ends in <code>1011</code>, whose
last symbol is a <code>1</code>, so one symbol of progress is already
banked. A <code>0</code> leaves the input ending <code>1010</code> —
two symbols of progress, not none.

Notice also that accepting is not permanent here. Run
<code>10101</code> and watch the machine enter, leave, and re-enter
the double circle. All that matters is where it stands when the
input runs out.

## Start with 1, end with 0

A composite rule. The machine has to remember *two* things:
"did the input start correctly?" and "what was the last symbol?" If
the very first symbol is <code>0</code>, the rule is broken
forever — the machine drops into the **dead** state and never
recovers.

<FSMRunner
  client:visible
  machine={startsOneEndsZero}
  defaultInput="1110"
  examples={["", "0", "1", "10", "11", "100", "1110", "1011", "0110"]}
/>

## A password machine

This machine accepts *only* the exact string <code>qrmt</code>. The
alphabet is shrunk to `{q, r, m, t, x}`, where <code>x</code> stands
for "any other letter." Every step except the right one drops the
machine into **dead**.

<FSMRunner
  client:visible
  machine={passwordQrmt}
  defaultInput="qrmt"
  examples={["q", "qr", "qrm", "qrmt", "qrmtx", "qrmq", "x"]}
/>

Notice what happens once you type the correct string: a single
extra symbol — even another <code>q</code> — sends the machine to
**dead**. The machine accepts <code>qrmt</code> and *only*
<code>qrmt</code>.

## At least two 1s

A counter that stops counting at two. The machine has three moods:
*zero <code>1</code>s seen*, *exactly one <code>1</code> seen*, and
*two-or-more*. Once we are in the third mood, no input — zero or
one — can knock us out. That trap is the *good* one: it locks
acceptance in.

<FSMRunner
  client:visible
  machine={atLeastTwoOnes}
  defaultInput="0110"
  examples={["", "0", "1", "11", "0010", "1010", "1111"]}
/>

## Even number of zeros

Parity is the simplest interesting property. We need exactly one
bit of memory: *is the count of zeros even or odd?* Zero is even,
so <code>E</code> doubles as the start *and* the accepting state.
Reading a <code>0</code> flips the parity; reading a <code>1</code>
leaves it alone.

<FSMRunner
  client:visible
  machine={evenZeros}
  defaultInput="11011"
  examples={["", "0", "1", "00", "01", "11", "0011", "11011", "0010"]}
/>

## Every block of 1s has even length

Call an uninterrupted stretch of <code>1</code>s a *block*. In
<code>0110011</code> the blocks are <code>11</code> and
<code>11</code>; in <code>0111011</code> they are <code>111</code>
and <code>11</code>. This machine accepts exactly when every block
has even length.

<FSMRunner
  client:visible
  machine={evenBlocksOfOnes}
  defaultInput="0110011"
  examples={["", "0", "11", "0110011", "1", "010", "111", "0111011"]}
/>

This one is worth sitting with, because it separates two things
that are easy to run together. The mood <code>odd</code> is *not*
accepting — but it is not hopeless either: one more <code>1</code>
and the block is even again. A <code>0</code> arriving there is a
different matter. It *closes* a block of odd length, and no later
symbol can undo that, which is exactly what <code>dead</code> is
for.

"Not accepting" and "doomed" are different conditions, and a
machine needs different moods for them.

## Length at most 4

A pure counter. Each symbol — whatever it is — bumps the state one
notch along the chain. After four symbols any further input falls
into **dead**. Five accepting states (including the empty-string
state) and one trap.

<FSMRunner
  client:visible
  machine={lengthAtMost4}
  defaultInput="aaa"
  examples={["", "a", "aa", "aaa", "aaaa", "aaaaa", "aaaaaaa"]}
/>

## Number of 1s divisible by 3

Now we lift the count to *modulo* arithmetic. Three moods record
*the count of <code>1</code>s, mod 3*. Reading a <code>0</code>
loops in place; reading a <code>1</code> rotates around. Only
<code>r0</code> is accepting.

<FSMRunner
  client:visible
  machine={divisibleBy3Ones}
  defaultInput="111"
  examples={["", "1", "11", "111", "1010", "111111", "10101010"]}
/>

The machine cannot remember *how many* <code>1</code>s it has seen
— only the count modulo three. To remember an exact count we'd
need a fresh state for every possible count, and that ladder would
never end. Hold that thought; it returns at the end of the chapter.

## Divisible by 5

So far our counters have counted symbols. This one reads a
*number*. A string of <code>0</code>s and <code>1</code>s can be
read left to right by a single rule: **start at 0, and on each new
digit, double what you have and then add the digit.** So
<code>1011</code> runs 0 → 1 → 2 → 5 → 11.

The number itself grows without limit, so the machine cannot
remember it — and does not need to. To know whether the final
number is divisible by 5, it is enough to remember the *remainder*
on division by 5, and there are only five of those. From remainder
*i*, reading digit *d* lands on the remainder of 2*i* + *d*.

<FSMRunner
  client:visible
  machine={divBy5Binary}
  defaultInput="1010"
  examples={["0", "101", "1010", "1111", "", "1", "10", "1011"]}
  width={600}
/>

The extra <code>start</code> mood exists for one reason only: it
behaves exactly as <code>R₀</code> does, but it is not accepting,
which is what keeps the empty string out.

## An alternating sum

Given a string *s*₁*s*₂…*s*<sub>k</sub> of <code>0</code>s and
<code>1</code>s, form its **alternating sum**: add the first
symbol, subtract the second, add the third, subtract the fourth,
and so on. This machine accepts exactly when

<div style={{textAlign:'center', margin:'8px 0', fontFamily:'ui-monospace, monospace'}}>
s₁ − s₂ + s₃ − s₄ + … is divisible by 3.
</div>

Note the sum can be negative — for <code>01</code> it is
0 − 1 = −1 — so "divisible by 3" means the usual thing for whole
numbers of either sign.

The state's letter (A or B) tracks whether the *next* symbol sits
at an odd or an even position; the subscript is the running
remainder. The machine alternates between the two layers as it
reads, *adding* at A-states and *subtracting* (the same as adding
2, mod 3) at B-states.

<FSMRunner
  client:visible
  machine={divBy3Binary}
  defaultInput="110"
  examples={["", "0", "11", "110", "1001", "1100", "111111", "10101"]}
  width={600}
/>

The accepting states are <code>A₀</code> and <code>B₀</code>: the
running remainder is zero whether the next symbol would sit at an
odd or an even position. The diagram is dense by design — six
states, twelve transitions — but every arrow is just one of the
four arithmetic rules above.

It is worth saying why this particular condition is worth
checking at all. Read the string as the binary representation of
a number *n*, and *n* turns out to be divisible by 3 exactly when
this alternating sum is — the binary cousin of the familiar rule
that 121 is divisible by 11 because 1 − 2 + 1 = 0. So the machine
above is, in disguise, a recognizer for the multiples of 3
written in binary.

## Substring detection: "bfs"

The job: accept exactly those strings that contain
<code>bfs</code> somewhere inside. The machine's states track the
*longest prefix of <code>bfs</code> we have just seen* — empty,
<code>b</code>, or <code>bf</code> — plus a fourth, *we have seen
the whole thing*, which is a one-way trap. Alphabet: `{b, f, s, x}`,
with <code>x</code> standing in for any other letter.

<FSMRunner
  client:visible
  machine={substringBfs}
  defaultInput="bfs"
  examples={["bfs", "abfsx", "bbfs", "bfbfs", "bfx", "fsbfs", "bbb", "ssss"]}
/>

The transitions are all about *keeping hope alive*. A
<code>b</code> always lets us start a fresh attempt; a stray
<code>f</code> or <code>s</code> from the empty mood does nothing.
Once we have seen the whole substring we lock into accept.

## The second-to-last symbol

This looks like the very first recognizer we built, but it is a
different animal. There the answer was decided by the last symbol,
which the machine could simply hold on to. Here it must know a
symbol that is *not* the last one — and while reading it cannot
know which symbol will turn out to be second-to-last.

The way out is to remember the last *two* symbols at all times.
Four possibilities, four moods. The mood named <code>ab</code>
means the last two symbols read were *a* then *b*; reading *c*
slides the window along, <code>ab</code> → <code>bc</code>, and the
oldest symbol is forgotten because it can never be needed again.

<FSMRunner
  client:visible
  machine={secondToLastIsOne}
  defaultInput="0111"
  examples={["10", "11", "010", "0111", "", "1", "001", "100"]}
/>

We pretend two <code>0</code>s were read before the string began,
which costs nothing and conveniently makes strings of length 0 and
1 come out rejected, as they should. The accepting moods are
<code>10</code> and <code>11</code> — exactly those whose *first*
remembered symbol is a <code>1</code>, since that is the
second-to-last symbol of the input.

Wanting the *third*-to-last symbol needs a window of three, and so
eight moods. Bigger, but not one bit cleverer.
